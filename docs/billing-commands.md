# Hosting billing and trial recovery

`dvmctl billing status` reads the platform's billing-state version 1 without buying a plan, creating an account, starting a trial, or changing a restriction. Output is JSON by default; add `--human` for prose on stderr, including relevant amounts, deadlines, next steps, and the request trace ID. The JSON response retains canonical money units, service periods, reservations, cost breakdowns, coverage, deadlines, restriction codes, and all allowed next actions. Unknown coverage is not zero usage. Read every restriction: paying one balance does not remove other holds.

| Command | Action |
| --- | --- |
| `billing status` | Inspect billing, trial admission, allowances, and recovery. |
| `billing budget get` | Read the budget and its concurrency version. |
| `billing budget set <usd-cents\|none> --expected-version <n> --idempotency-key <key>` | Explicitly set or remove a budget. The platform enforces authorisation and plan eligibility. |
| `billing topup <usd-cents> --idempotency-key <key>` | Explicitly request a Lightning hosting invoice; minimum 1000 USD cents. |
| `billing topup-status <id>` | Poll an existing hosting top-up once. |
| `billing plan quote <plan-id> --request-key <key>` | Obtain a plan-change quote without purchasing. Requires an existing settled paid term. |
| `billing plan purchase <quote-id> --rail stripe\|lightning` | Explicitly purchase a saved quote. |
| `billing plan status <quote-id>` | Inspect or reconcile an already requested plan change. |
| `billing checkout <plan-id> --rail stripe\|lightning [--months 1\|3\|6\|12]` | Explicitly request checkout, including a trial-to-paid conversion. Months apply only to Lightning. |
| `billing invoice <invoice-id>` | Poll an existing Lightning subscription invoice once. |
| `trial export <slug> [--port <port>] [--machine <id>]` | Open the existing read-only database tunnel during the seven-day recovery window. |
| `trial restore <slug>` | Request restore after verified purchase, including after the seven-day recovery deadline if a paid plan was purchased before it; never purchase or reset the trial. |

All commands accept `--human` and `--org <handle>`. Organisation selection, including the context saved by `dvmctl switch`, applies to status, budgets, top-ups, Stripe checkout, and trial recovery. The platform's plan-change and Lightning subscription routes bill only the authenticated key's account. Those commands reject a selected organisation rather than charging another account. Use a key for the intended account and `dvmctl switch --personal` for those routes. Organisation keys cannot edit budgets; the platform requires an authorised builder key.

Save the idempotency key before a top-up or budget write and reuse the exact arguments after an interruption. Keys contain 8–128 letters, digits, underscores, or hyphens. A budget update also requires the version observed by `budget get`; a conflict requires reading the budget before deciding on a new mutation. Save the request key when creating a quote, and reuse that key and target to retrieve the same quote. Purchase retries use the saved quote id. Renewal-downgrade quotes require the platform's scheduling workflow; this CLI does not schedule them.

A hosted Stripe URL or Lightning invoice is a human payment step. It is never proof of payment. Output includes the invoice id or URL and a `continuation.status_command` argument array. Hosting top-up output retains both the USD hosting value and the native invoice amount, plus invoice expiry timestamps in Unix milliseconds. Subscription Lightning checkout and invoice output retains `fiatCurrency` and `planUsdCents` when supplied. `amount_display` labels `amountCents` in that reporting currency; `plan_usd_display` shows the canonical USD plan value before subscription credit and excluding compute overage, or null when unknown. Invalid currency codes are shown beside the raw minor-unit amount, preserving the invoice id for continuation. On older platforms without these fields, the invoice currency is explicitly unstated and never assumed to be USD. Plan-change purchases use the saved quote currency. Quote output uses the quote's currency. A top-up's `quote.expiresAt` and `providerExpiresAt` are separate authorities and both remain visible. Only the platform's `paid` top-up status confirms credit; subscription statuses such as `payment_received` and `payment_recovery` still need reconciliation.

Resume an interrupted Lightning flow with `billing invoice <invoice-id>` or `billing topup-status <id>`, not another checkout. Stripe and Lightning subscription checkout do not accept idempotency keys on this platform; dvmctl does not retry those POST requests automatically. Inspect billing and any saved invoice before explicitly requesting another checkout.

For an expired trial, inspect `billing status`, then run `trial export <slug>` while recovery remains available. Keep the command running, and supply its `database_url` to `pg_dump` to write an export file. That URL contains temporary credentials; keep it private. The platform makes the recovery login read-only and ends the socket by the original recovery deadline. An export failure or retry does not extend that deadline. Use explicit `billing checkout` to buy a paid plan, confirm payment, then run `trial restore <slug>`. Other holds can still prevent restore; `trial_restore_blocked` relays the platform display. The restore response does not carry restriction reasons. When the follow-up billing-state read succeeds, dvmctl copies its restriction rows into `reasons`; those rows can include holds on other DVMs in the account. If the read fails, the reasons are unavailable. A `trial_recovery_closed` response means the recovery window ended; it does not assert that the DVM was destroyed.

Deploy, scale, and resume refusals preserve `reasons`, `display`, `hint`, and `options`. For hosting admission codes or refusals carrying restriction reasons, if no next actions are supplied, dvmctl follows the refusal with a billing-state read for the same account. The refusal keeps its own trace id, with the billing read identified separately as `billing_state_trace_id`. The original refusal remains authoritative if that follow-up fails, with `billing_state_error` and a status-command continuation.

An unknown billing-state version produces `billing_version_unsupported` and asks for a dvmctl upgrade before interpreting the response. Unknown reason and action codes in version 1 pass through. A missing gated route on an older platform produces `billing_not_available`: the feature is not available on that platform. A JSON `not_found` response means the invoice, quote, or top-up identifier is absent or inaccessible. A plain-text 404 on those gated status routes means the feature is unavailable on that platform.
